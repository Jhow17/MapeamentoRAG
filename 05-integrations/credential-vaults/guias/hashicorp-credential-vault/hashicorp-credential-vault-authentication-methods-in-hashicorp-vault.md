# Setting up HashiCorp vault and acquiring authentication credentials

In the HashiCorp vault, choose your authentication method and record the authentication credentials to use later for your vault instance in Securiti.

### Supported authentication methods for HashiCorp vault

Following authentication methods are supported for the HashiCorp vault.

| Authentication method | Authentication credentials | mTLS support |
| --- | --- | --- |
| AppRole | - AppRole ID - Role Secret | Supported |
| AWS IAM Role | - Vault AWS IAM Role - AWS IAM Server ID Header - AWS IAM Role Mount Path | Not supported |
| Username & Password | - Username - Password | Supported |

# Storing data system credentials in HashiCorp vault

### Acquiring authentication credentials for HashiCorp vault

Log into your HashiCorp account and record or configure the following authentication credentials:

- **Host**: Record the the URL or IP address of the HashiCorp vault instance.
- **Port**: Record the port number on which the HashiCorp vault server is listening. The default port is usually *8200*, but it can vary depending on your server configuration.
- **Namespace**: Record the namespace for your tenant within the HashiCorp vault Enterprise environment for e.g, "teamB/engineering".

This is an optional parameter required when using isolated environment(s) in the vault. See [HashiCorp vault enterprise namespaces documentation](https://developer.hashicorp.com/vault/docs/enterprise/namespaces), for more information.

#### Using AppRole authentication

#### 

Follow the below procedure to create a Policy and an AppRole using the Vault CLI.

1. Enable the AppRole authentication on your Vault server, if not already. Run the below command:

```bash
vault auth enable approle
```
2. Create a policy with read-only access. This policy lets the AppRole to list and read secrets from the secret/ path, where connector credentials are typically stored.
  1. Create a policy file named `securiti-read-secrets.hcl` with the following content:

```bash
# securiti-read-secrets.hcl
# This policy grants read-only access to all secrets under the default 'secret/' path.
path "secret/*" {
  capabilities = ["read", "list"]
}
```
  2. Apply or write this policy to the Vault. We recommend including the role name in the policy name for clarity. Replace `&lt;role-name&gt;` with a name for your AppRole for example, `securiti-role`.

```bash
vault policy write read-<role-name>-policy read-secrets-policy.hcl
```
3. Create the AppRole and attach the read-only policy to it using the command below. This command also configures how long the generated credentials stay valid.

```bash
vault write auth/approle/role/<role-name> \
    token_policies="<role-name>-policy" \
    secret_id_ttl="8760h" \
    token_ttl="1h" \
    token_max_ttl="4h"
```

In the command above,

> [!NOTE]
> **Note**
> 
> By default, the HashiCorp vault enables the AppRole method at the path `auth/approle/`. If you are using a custom path such as, `auth/my-approle/`, record it to use later during connector authentication process.
  - `token_policies` links the policy you created previously.
  - `secret_id_ttl="8760h"`, sets the Secret ID's validity period to one year.
  - `token_ttl` and `token_max_ttl` control the validity of the temporary access tokens generated by the AppRole. You can adjust these values as needed.
4. Generate the **App Role ID** by executing the below command. Record the `role_id` from the output.

```bash
vault read auth/approle/role/<role-name>/role-id
```

The **App Role ID** is the unique identifier for your AppRole and is one of the two credentials needed for authentication.
5. Generate the **Secret** ID by executing the below command. The output generates `secret_id_accessor` and `secret_id`. Record the `secret_id` from the output.

```bash
vault write -f auth/approle/role/<role-name>/secret-id
```

The **Secret** ID is the second credential required for authentication. It acts like a password for the AppRole.

#### Using AWS IAM Role authentication

For **AWS IAM Role** authentication method, following parameters are needed:

- **Vault IAM role name**:

Create the IAM role in the vault and bind it to provide access to the ec2 instance role assigned to the appliance VM node. All nodes in the cluster must have the same ec2 instance role.

Example vault role creation command:

```bash
vault write auth/aws/role/dev-role-iam auth_type=iam bound_iam_principal_arn="arn:aws:iam::162495643159:role/VAULT_CLIENT" policies=secret_policy ttl=15m
```

Output:

```plaintext
Success! Data written to: auth/aws/role/dev-role-iam
```

In the command above, `arn:aws:iam::162495643159:role/VAULT_CLIENT` is the ec2 instance role assigned to the appliance VM and `secret_policy` is the policy that controls the permissions to the vault client (appliance). You can define policies as described in the HashiCorp vault documentation and based on the level of access you are willing to grant.
- Obtain the **AWS IAM Server ID Header** (if you have configured a header)
- Obtain the **AWS IAM Role Mount Path** (if you have used a path other than the default, which is "AWS"). The mount path is the path in HashiCorp vault where the AWS IAM authentication method is enabled. It is used to identify where in the vault the IAM role is configured.

#### Using Username & Password authentication

For **Username & Password** authentication method, you must configure the **userpass** authentication using vault CLI:

1. Enable the authentication by using the command below.

```bash
vault auth enable userpass
```
2. Once the **userpass** auth is enabled, create a policy to assign permissions to the users by running the command below.

```bash
vault policy write user-pass -<<EOF
path "secret/*" {
    capabilities = ["read"]
}
EOF
```

The above command creates a policy named **user-pass** which reads all secrets with path starting **secret/**.
3. Create a new user with the policy created above using the command below.

```bash
vault write auth/userpass/users/securiti policies=user-pass
password=mypassword
```

This command creates a user with the username **securiti** and password **mypassword**, and attaches the **user-pass** policy for permission.

Record the **Username** and **Password** to use later.

### Using mTLS authentication with HashiCorp

Mutual TLS (mTLS) is a security protocol that requires both the client and server to authenticate each other using certificates. This ensures that both parties are trusted, providing a higher level of security compared to standard TLS, which authenticates only the server. Securiti supports mTLS authentication with HashiCorp for Pod versions 1.132 and above, with the following authentication methods:

- AppRole
- Username & Password

To use mTLS authentication with HashiCorp, you must acquire the X.509 certificates and private keys that are used for client authentication with HashiCorp Vault. Following paths are required when configuring the HashiCorp vault instance in Securiti with mTLS enabled.

- **Client Certificate Path**: Record the path that points to the PEM-formatted client certificate file, which can be generated and signed by Vault’s PKI engine, issued via cert-manager in Kubernetes, or obtained from an external CA.
- **Client Key Path**: Record the path that points to the PEM-formatted private key file corresponding to the client certificate, generated locally or by Vault’s PKI engine, and must be securely stored.

Both files are typically stored on the client system or container and their paths are configured in Vault’s mTLS settings to enable mutual TLS authentication. These files must be accessible to Securiti connector authenticating via **AppRole** or **Username & Password** with mTLS enabled, ensuring secure and trusted communication with the HashiCorp Vault server. For more information, see [HashiCorp's Consul Core documentation](https://developer.hashicorp.com/consul/docs/secure/security-model/core).
