# Implement APIs for the user-defined connector

To configure a user-defined Connector, you must first implement two APIs; one for initial requests, and a second to accept polling for the status of those requests, as described in the following sections. Securiti returns result in a zip file format. For Authentication, you can implement either a basic (username and password) or API key.

Authorization header logic works the same for both Self-hosted and Securiti Cloud Webhooks.

| Authentication type | Header information |
| --- | --- |
| Basic Authentication | Securiti sends the Authorization as a header to your webhook server. For example, If username is *admin* and password is *PrivateEntity@123*. The Header key and value would be as follows: - **Key**: Authorization - **Value**: Basic base64 (admin:PrivateEntity@123). It translates to the following header in the request: ```plaintext Authorization: Basic YWRtaW46UHJpdmF0ZUVudGl0eUAxMjM= ``` |
| Apikey Authentication | Securiti use the following header to send the Authentication Credentials to your webhook server For example, if Api key is *abcdefghij1234567890*. The Header key and value would be as follows: - **Key**: X-API-Key - **Value**: abcdefghij1234567890. It translates to the following header in the HTTP request. ```plaintext X-API-Key: abcdefghij1234567890 ``` |

`POST /opengdpr_requests`


Where:

| `subject_request_id` | A UUID generated by the DSR Workflow. |
| --- | --- |
| `subject_request_type` | One of the three valid DSR request types: - access - port - erasure |
| `submitted_time` | Time of submission as a string (we can also opt for a standard format or just UTC timestamp). |
| `api_version` | API version in case there are more than one implementations available. |
| `subject_identities` | Identities of the data subject for whom Securiti has generated the DSR. |

Your request API must return the following response:

```plaintext
{   "controller_id":"example_controller_id",
    "expected_completion_time":"2018-11-01T15:00:01Z",
    "received_time":"2018-10-02T15:00:01Z",
    "encoded_request":"<BASE64 ENCODED REQUEST>",
    "request_status":"cancelled",
    "subject_request_id":"a7551968-d5d6-44b2-9831-815ac9017798"
    "results_url":""
}
```

Where:

| `controller_id` | Controller id that will be processing this request |
| --- | --- |
| `expected_completion_time` | Estimated time when the request will be completed. |
| `receive_time` | Time when the request was received by controller. |
| `encoded_request` | (Optional) Base 64 encoding of the entire body of the OpenGDPR request. Controllers must not log or store this value. |
| `request_status` | One of the following statuses: - `pending` - `in_progress` - `completed` - `cancelled` If the status is `completed` or `cancelled`, Securiti stops polling for the request. |
| `subject_request_id` | Subject request id received in the request. |
| `results_url` | Where the `subject_request_type` is `access` or `port`, and the `request_status` is `completed`, the POST response must include a `results_url` from which Securiti can download the results of the DSR request. |

### Polling API

Your API endpoint must accept the following polling payload to query the status of an existing DSR request:

`GET /opengdpr_requests/a7551968-d5d6-44b2-9831-815ac9017798`

Your API must provide the following response:

```plaintext
{
    "controller_id":"example_controller_id",
    "expected_completion_time":"2018-11-01T15:00:01Z",
    "subject_request_id":"a7551968-d5d6-44b2-9831-815ac9017798",
    "request_status":"pending",
    "api_version":"1.0",
    "results_url":"https://exampleprocessor.com/secure/d188d4ba-12db-48a0-898c-cd0f8ba7b345"
}
```

Where:

| `controller_id` | Controller ID that will be processing the request. |
| --- | --- |
| `expected_completion_time` | Estimated time when the request will be completed. |
| `subject_request_id` | The subject request ID that was previously submitted in a DSR request. |
| `request_status` | One of the following statuses: - `pending` - `in_progress` - `completed` - `cancelled` If the status is `completed` or `cancelled`, Securiti stops polling for the request. |
| `api_version` | The API version in case there are more than one implementations available. |
| `results_url` | Where the `subject_request_type` is `access` or `port`, and the `request_status` is `completed`, the polling response must include a `results_url` from which Securiti can download the results of the DSR request. If the `request_status` is `pending`, the `results_url` may be included but empty. |

> [!NOTE]
> **Note**
> 
> Your API endpoint must also accept just `GET /opengdpr_requests/` with no payload, and return an empty response body and status 200 OK

> [!NOTE]
> **Note**
> 
> If the results_URL your API provides ends in a slash, Securiti appends a slash at the end of the request ID when it queries the URL for the results. Likewise, if the URL ends without a slash, Securiti omits the slash from the end of the query.
> 
> For example, if your results_url is:
> 
> `https://blrqaauto.pythonanywhere.com/opengdpr_requests/`
> 
> Our query would use
> 
> `https://blrqaauto.pythonanywhere.com/opengdpr_requests/e2f626a6-8d3d-4c96-9b4d-77f12742506e/`
> 
> If your results_url is:
> 
> `https://blrqaauto.pythonanywhere.com/opengdpr_requests`
> 
> Our query would use:
> 
> `https://blrqaauto.pythonanywhere.com/opengdpr_requests/e2f626a6-8d3d-4c96-9b4d-77f12742506e`
