# Understanding analyzers, rules, and policies

Firewall rules are a set of evaluations within a firewall that analyze:

- User messages sent to the LLM
- Retrieval documents sent to the LLM (LLM and the source data)
- Responses generated by the LLM and sent to the user

Analyzers generate metadata that rules can evaluate. Text analyzers are used in natural language processing (NLP) to analyze text data. They can perform tasks such as sentiment analysis, topic detection, entity recognition, and syntax analysis. Text analyzers help in understanding, interpreting, and manipulating human language in a way that is useful for further processing and decision-making.

When a user enters a prompt or a message, the analyzers generate payload analysis information about the message. For example, the language analyzer analyzes the language the message was entered in.

The analyzers and rules have many-to-many relationships. Some analysers may power multiple rules e.g. the same rule may trigger jailbreak, PII fishing, IP infrastructure phishing policy.

### Open Policy Agent (OPA) and Policies

Open Policy Agent (OPA) is an open-source policy engine that lets you write policies as code. These policies, written in the Rego language, can be used to make decisions across various services.

Policies are configurable rules and actions. Each policy can have multiple rules. Each rule is modifiable Rego code. The OPA Configurator dynamically generates policies for pipelines in the following manner:

1. Rules are built from the rules collection
2. Policies are built from the policies collection
3. Rules with default parameters should use the values defined for that rule
4. Rules with non-defaulted parameters should use values defined in the policy for that rule
5. Policies enabled for a Pipeline are enforced for messages for that pipeline

### Configuring policies with OPA

To implement a policy:

1. **Define the policy package**: Specify a package name. This helps in organizing and referencing the policy.
2. **Set default values**: Define default values for the rules, which serve as fallbacks if no conditions are met.
3. **Write the rules**: Define the rules with specific conditions that need to be evaluated. Each rule should return a boolean value indicating whether the condition is met.
4. **Load and test the policy**: Load the policy into OPA and test it with various inputs to ensure it works as expected.

An example of a policy (in a casual format) is:

```plaintext
block if [phishing or login or api] 
warn  if [email]
log   if –
pass  otherwise
```

All analyzers may have a different payload configuration, however, the following metadata should be present in any analyzer. Any analyzer that returns "status": "FAILURE" should be ignored and no rules should be triggered.

```json
"analysis_metadata": 
  {
    "status": "<str; one of SUCCESS, FAILURE>"
  }
```

Any analyzer with an associated REDACT policy must have a redaction payload format, which is as follows:

```json
"redaction_information": 
  [
    {
        "value": "<str; text of the detection to be redacted>",
        "redacted_value": "<str; value to be redacted to>",
        "detection_type": "<str; the detection type>",
        "offset": "<int; the character offset where the detection begins>"
    },
    …
  ]
```

### Securiti Analyzers

Securiti’s Gencore AI has built-in analysers that may be used to create or customize rules.

> [!NOTE]
> **Note**
> 
> Users cannot create new analyzers and must use existing, built-in analyzers to configure rules. However, the customer can write a rule that is a regular expression supported by Rego.

Securiti supports the following analyzers:

**Language Analyzers**: Used to process, interpret, and understand human language. They are commonly used in natural language processing (NLP) and computational linguistics to analyze text and speech data.

```json
"language_analyzer": 
  {
    "analysis_metadata": <metadata>,
    "language": {
      "detected": ["<str; ISO-639-1>", "<str; ISO-639-1>", "..."],
    }
  }
```

**Exemplar Analyzer**: Analyzes the user message or prompt and attempts to locate a match in the existing, pre-configured exemplar topics.

```json
"exemplar_analyzer": 
  {
    "analysis_metadata": <metadata>,
    "exemplar": {
      "<topic>": {
        "negative_similarity": "<float; in 0-1>",
        "positive_similarity": "<float; in 0-1>",
        "llm": "<optional str; one of {NEGATIVE, POSITIVE, NONE}>"
      }
    }
  }
```

**Sensitive Data Analyzer**: Examines the entered message or prompt for sensitive data that may include personal identifiable information (PII), financial data, health records, intellectual property, and other confidential information.

```json
"sensitive_data_analyzer":
  {
    "analysis_metadata": <metadata>,
    "redaction_information": <redaction_information>,
    "sensitive_data": {
        "detections": {
              "<data element type>": {
                  "unique_values": ["<str; value1>", "<str; value2>"],
                  "count": <int; count>,
              },
              "<data element type>": {
                  "unique_values": ["<str; value1>", "<str; value2>"],
                  "count": <int; count>,
              },
              …
              "<data element type>": {
                  "unique_values": ["<str; value1>", "<str; value2>"],
                  "count": <int; count>,
              },
              "<data element type>": {
                  "unique_values": ["<str; value1>", "<str; value2>"],
                  "count": <int; count>,
              },
              …
        }
    }
  }
```

**Source Code Data Analyzer**: Analyzes source code that may be entered as a prompt. The source code analyzer is invoked if any rule or policy concerning source code is active and determines if source code is present.If that rule is active then the source code analyzer is run regardless of whether or not source code is passed.This analyzer determines the amount of source code the message contains and triggers if the volume of source code in the message exceeds the specified threshold, captured as "significant", "some", and "snippet".

```json
"source_code_analyzer":
  {
    "analysis_metadata": <metadata>,
    "source_code": {
        "qualitative_amount": "<str; one of {NONE, SNIPPET, SOME, SIGNIFICANT}>"
    }
  }
```

**Sentiment Data Analyzer**: Analyzes a message for negative or positive sentiments in a text. In case of negative sentiment, it triggers a rule if the confidence of the message containing such content exceeds the specified threshold.

```json
"sentiment_analyzer":
  {
    "analysis_metadata": <metadata>,
    "sentiment": {
        "linguistic_analysis": {
            "sentiments": ["<str; one of ANGER, ANTICIPATION, DISGUST, FEAR, JOY, NEGATIVE, NEUTRAL, POSITIVE, SADNESS, SURPRISE, TRUST">, …]
        }
        "semantic_analysis": {
            "negativity_score": <float; >
        }
    }
  }
```

**Toxicity Data Analyzer**: Analyzes a message for offensive/toxic content and triggers if the confidence of the message containing such content exceeds the specified threshold.

```json
"toxicity_analyzer":
  {
    "analysis_metadata": <metadata>,
    "toxicity": {
        "semantic_analysis": {
            "toxicity_score": <float; >
        }
    }
  }
```

**Off Topic Analyzer**: Analyzes the topic of a message and triggers if the confidences of all of the specified topics fall below a specified threshold.

```json
"off_topic_analyzer":
  {
    "analysis_metadata": <metadata>,
    "topics": {
        "linguistic_analysis": {
            "is_off_topic": <boolean>
        }
    }
  }
```

**Secrets Analyzer**: Detects authentication secrets, such as API keys, in a message and triggers a rule if any are found.

```json
"secrets_analyzer":
  {
    "analysis_metadata": <metadata>,
    "redaction_information": <redaction_information>,
    "secrets": {
        "n_secrets": <int>,
    },
  }
```

**Login Credentials Analyzer**: Detects usernames and passwords in a message. The rule triggers if the number of usernames or the number of passwords exceeds their specified thresholds.

```json
"login_analyzer":
  {
    "analysis_metadata": <metadata>,
    "redaction_information": <redaction_information>,
    "login_credentials": {
        "n_usernames": <int>,
        "n_passwords": <int>
    }
  }
```

**Malicious URL Analyzer**: Analyzes a message for the presence of malicious URLs and triggers if the classification confidence of containing one exceeds a specified threshold.

```json
"malicious_url_analyzer":
  {
    "analysis_metadata": <metadata>,
    "redaction_information": <redaction_information>,
    "malicious_urls": {
        "malicious_url_likelihood": <float>,
    }
  }
```

**Prompt Injection Analyzer**: Analyzes a message for the presence of a prompt injection attack and triggers if the classification confidence of containing one exceeds a specified threshold.

```json
"prompt_injection_analyzer":
  {
    "analysis_metadata": <metadata>,
    "prompt_injection": {
        "prompt_injection_likelihood": <likelihood; float>,
    }
  }
```

**General Topic Analyzer**: Analyzes the prompt with a list of approved topics. The rule triggers if its topic does not match any in this list.

```json
"general_topic_analyzer":
  {
    "analysis_metadata": <metadata>,
    "topics": {
        "<topic_name; str>": <likelihood; float>,
        ...
    }
  }
```

**Refusal Analyzer**: Triggers a rule if the LLM refuses to respond to a request, which may indicate if prohibited requests are sent to it.

```json
"refusal_analyzer":
  {
    "analysis_metadata": <metadata>,
    "refusal": {
        "refusal_likelihood": <likelihood; float>
    }
  }
```

**Jailbreak Analyzer**: Lets you detect and analyze attempts to bypass security restrictions in your AI models and applications.

```json
"jailbreak_analyzer":
  {
    "analysis_metadata": <metadata>,
    "jailbreak": {
        "jailbreak_likelihood": <likelihood; float>
    }
  }
```

**Safety Topic Analyzer**: Analyzes a message for general malicious intent across exemplar-based threat categories and Purple Llama safety categories, and triggers when the confidence score exceeds a configured threshold.

```json
"safety_topic_analyzer":
  {
    "analysis_metadata": <metadata>,
    "topics": {
        "<topic_name; str>": <likelihood; float>,
        ...
    }
  }
```

#### Creating a custom rule for language detection

Creating a rule using Rego involves writing a policy in the Rego language, which is then evaluated by the Open Policy Agent (OPA).

The following example shows creating a simple language rule that allows user prompts in the English language only and blocks all the sprompts that are in any other language.

**Code Structure:**

The policy engine expects the Rego code to be encapsulated in `rule_match(_)` function.

```json
rule_match(_) {
    # write custom Rego code here
}
```

This function acts as an entry point for evaluation of any rule. You can declare variables outside of this function but the custom rule must have at least one `rule_match(_)` function.

**Using Securiti Analyzers**:

In order to implement language restrictions, you must know the analysis performed by the analyzers. The analyzers generate metadata/analysis and pass this information to the rule. You can read this analysis using `input.analysis`{analyzer_name}. For language rule, the example uses the language analyzer that provides the following information.

```plaintext
input.analysis.language_analyzer.analysis_metadata.status
input.analysis.language_analyzer.language.detected
```

`analysis_metadata.status` identifies if the analysis is performed successfully.

`language.detected` dentifies the language detected by the analyzer.

**Rego Code for Language rule:**

Now we use the above information in our Rego code.

```plaintext
#declare allowed language
allowed_language = “en”

rule_match(_) {
    input.analysis.language_analyzer.analysis_metadata.status == “SUCCESS”
    input.analysis.language_analyzer.language.detected[0] == allowed_language
}
```

A firewall serves as a protective barrier between the user prompts and the LLM and between the LLM and the source data.

Securiti policies translate data intelligence into actions. Each policy has rules that, when matched by a file, document, or resource, trigger a response.

An exemplar is an example or model that is considered representative of a broader category, concept, or standard.
